# Remote Datapack

[![Buy Me a Coffee](https://img.shields.io/badge/Buy_Me_a_Coffee-Support_Manafield-FFDD00?style=for-the-badge&logo=buymeacoffee&logoColor=000000)](https://buymeacoffee.com/manafield)

Minecraft/Paper **26.3**, Java **25**용 단일 JAR 플러그인입니다.

## 현재 기능

- `/remotedatapack` 또는 `/rdpack`: 접속 중이며 `remotedatapack.manage` 권한을 가진 플레이어에게 본인용 일회용 링크 발급. 권한 기본값은 `op`입니다.
- `/rdpack status`: 본인의 링크·세션 개수와 웹 구동 상태. 콘솔에서는 구동 상태만 확인합니다.
- `/rdpack revoke`: 해당 플레이어의 모든 미사용 링크와 웹 세션 회수.

## 사용 예시

1. 게임에 접속한 관리자가 `/rdpack`을 입력합니다. `remotedatapack.manage` 권한이 필요하며 기본값은 OP입니다.
2. 채팅에 표시된 일회용 링크를 60초 안에 엽니다. 인증되면 계정명과 스킨 얼굴이 표시됩니다.
3. ZIP을 선택해 추가하거나 기존 ZIP을 교체합니다. 여러 파일을 변경해도 게임 데이터는 자동으로 리로드되지 않습니다.
4. **변경사항 적용**을 누르고 변경 목록을 확인한 뒤 **확인 후 적용**을 누릅니다. 적용 종료 후 기본 30초의 서버 공통 쿨타임이 시작됩니다.
5. 게임에서 로그아웃하면 웹 세션도 종료됩니다. 재접속 후에는 `/rdpack`으로 새 링크를 발급받습니다.

스킨 이미지를 불러오지 못하면 이름의 첫 글자를 표시합니다.

```yaml
ui:
  server-name: "Manafield"
  session-poll-seconds: 5
apply:
  cooldown-seconds: 30
```

서버명과 쿨타임 설정 변경은 정상 서버 재시작 후 적용됩니다.

## 데이터팩 목록과 보호 정책

`packs.directory: auto`는 Paper 26.3의 `Server.getLevelDirectory()`가 가리키는 실제 메인 월드의 `datapacks/`를 사용합니다. 첫 번째 로드된 월드를 추측하거나 사용자 요청의 경로를 받지 않습니다. 명시 경로를 설정하려면 이 동일한 디렉터리의 정규화된 절대 경로여야 합니다. 다른 월드·경로, 안전하지 않은 경로 또는 지원하지 않는 파일시스템이면 로컬 연결을 포기하고 Paper 정보만 보호 상태로 표시합니다.

- **ZIP/폴더**: Paper 출처가 WORLD이고 `file/<단일 파일명>`과 실제 로컬 항목이 일치할 때만 연결합니다. 폴더는 루트 `pack.mcmeta` 존재 여부만 확인하며 내용을 파싱하거나 하위를 재귀 탐색하지 않습니다.
- **내장·플러그인 팩**: Paper의 출처 값으로 구분하고 보호합니다. 같은 파일명이 있어도 파일 조작 대상으로 취급하지 않습니다.
- **새 로컬 후보**: Paper 목록에 아직 없는 `.zip` 또는 메타데이터가 있는 폴더는 `서버 미인식`, 활성 상태 `확인 불가`로 표시합니다. ZIP이나 JSON의 유효성을 검사했다는 뜻이 아닙니다.
- **경로 보호**: 디렉터리 핸들을 이용한 `SecureDirectoryStream`과 NOFOLLOW_LINKS로 루트의 모든 경로 구성요소를 엽니다. 심볼릭 링크는 따라가지 않으며 ZIP 하드링크 또는 링크 수를 확인할 수 없는 파일은 보호합니다. Unix 링크 수를 읽을 때 디렉터리 핸들의 파일 식별자와도 비교합니다.
- **응답 정보**: 서버 경로·원본 API 경로 ID는 노출하지 않습니다. 항목 ID는 프로세스별 난수로 구분한 불투명 값입니다. 일치한 비필수 WORLD ZIP만 `modifiable`/`downloadable`을 제공하며 `deletable`은 비활성 ZIP에서만 true입니다. 실제 작업 시 ZIP 내용과 현재 권한을 다시 검증합니다. `protected`는 내장·폴더·필수 팩·미확인 위치 등의 추가 보호 사유를 구분합니다.

목록은 로그인 직후와 `목록 다시 조회` 버튼을 누를 때만 읽습니다. 매 틱 검사나 목록 백그라운드 폴링은 없습니다. 기존 세션 확인은 5초 간격으로 유지합니다. 동시에 1개 조회, 디렉터리 항목 최대 1,024개 검사, 응답 최대 512개로 제한하고 초과 시 목록이 일부임을 표시합니다.

Paper 메타데이터는 메인 스레드에서 불변 값으로 복사하고 파일 메타데이터 조회·JSON 생성은 HTTP 워커에서 수행합니다. 파일 조회 전후 세션·권한을 확인해 조회 도중 로그아웃해도 목록을 반환하지 않습니다. 오류 응답에 예외 메시지나 경로를 포함하지 않습니다.

`목록 다시 조회`는 현재 Paper 스냅샷과 로컬 후보를 다시 읽을 뿐 `refreshPacks()`, `setEnabled()`, `reloadData()`를 호출하지 않습니다. 파일을 외부에서 추가해도 서버가 인식한 활성 상태는 자동으로 바뀌지 않습니다.

## ZIP 파일 작업

- **추가**: `POST /api/packs/upload`, `Content-Type: application/zip`, 정확한 Content-Length, 원본 ZIP 본문. multipart/전송 압축/chunked는 지원하지 않습니다. 브라우저가 File 객체로 요청하며 서버는 `rd-<UUID>.zip` 새 이름을 붙입니다. 클라이언트 파일명이나 경로로 덮어쓰지 않습니다.
- **교체**: `POST /api/packs/{id}/replace`, ZIP 본문과 `X-Pack-Confirm`에 URL 인코딩한 정확한 기존 파일명. UI에서 파일명 재입력 후 확인합니다. 활성 ZIP도 교체할 수 있지만 실행 중인 게임 데이터는 바뀌지 않습니다.
- **삭제**: `DELETE /api/packs/{id}`, 같은 파일명 확인 헤더, 본문 없음. 활성·필수·내장·플러그인·폴더·미인식 팩은 거부합니다. 활성 팩 비활성화는 공식 일괄 API 제약으로 제한합니다.
- **다운로드**: `GET /api/packs/{id}/download`. 안전한 ZIP 전체를 먼저 검증하고 attachment로 스트리밍합니다. 세션이 취소되면 이후 청크 전송을 중단하지만 이미 받은 바이트는 회수할 수 없습니다.
- **작업**: 변경 요청은 수신이 끝나면 202와 작업 ID를 반환합니다. `GET /api/jobs/{id}`는 작업을 시작한 동일 웹 세션만 조회합니다. 최근 128개를 메모리에 보관하며 재시작 시 사라집니다. 수신·검증·백업·커밋·발견 갱신·적용 대기/실패 상태를 제공합니다. 변경 중 전체 파일 작업은 1개로 제한하고 다른 요청은 409로 거부합니다.

파일 수신·검증·백업·rename·삭제·다운로드는 전용 I/O 스레드 1개에서 수행합니다. HTTP 스레드는 업로드 수신/다운로드를 최대 8초 기다리며 파일 작업 자체 기한은 30초입니다. 느린 업로드는 실패할 수 있습니다. HTTP 성공 응답을 잃으면 작업 결과도 불명확할 수 있으므로 자동 재시도하지 말고 목록과 감사 로그를 확인하세요.

ZIP 제한은 최대 20 MiB(설정 1–20), 항목 10,000개, 중앙 디렉터리 4 MiB, 선언/실제 비압축 총량 128 MiB, 항목 압축 비율 100:1, `pack.mcmeta` 64 KiB, JSON 깊이 32입니다. 경로 조작·중복 항목·심볼릭 링크/특수 파일·Unix 링크 확장·암호화·CRC/크기 불일치를 거부합니다. ZIP64·다중 볼륨·아카이브 주석·알 수 없는 확장 필드도 보수적으로 거부합니다. 압축 내용은 버퍼로 검사할 뿐 파일로 추출하지 않습니다. 현대 `min_format`/`max_format` 숫자 또는 `[major, minor]` 형식으로 121.0 지원을 명시해야 하며 레거시 메타데이터 자동 변환은 하지 않습니다. 게임 함수의 의미나 안전성까지 검증하는 기능은 아닙니다.

교체/삭제 전 현재 ZIP을 검증하고 같은 디렉터리의 `.rd-backup-<파일명 SHA256>-<UUID>.bak`에 별도 복사합니다. 기본 팩당 3개(1–10), 전체 200 MiB(업로드 한도–1024 MiB)입니다. 총량은 새 백업까지 포함해 미리 확인하며 부족하면 원본을 바꾸지 않습니다. 다른 팩 백업을 자동 삭제하지 않습니다. 새 백업 검증 후 같은 팩의 오래된 백업을 정리합니다. 삭제 후에도 백업은 보관합니다. `.bak`와 `.rd-tmp-<UUID>.tmp`는 팩 ZIP으로 발견되지 않습니다. 중단된 임시 파일은 정상 실패/종료 때 정리하며, 강제 종료 잔여물은 다음 변경 작업 시작 시 제한된 이름만 정리합니다.

교체는 `SecureDirectoryStream.move()`의 원자적 rename만 사용합니다. 지원하지 않으면 부분 덮어쓰기로 대체하지 않습니다. 기존 원본 해시와 백업을 확인하고 변경 후 Paper `refreshPacks()`와 `getPack()`으로 발견 상태를 확인합니다. 갱신 실패 시 백업으로 복원하거나 새 ZIP을 제거합니다. 복원 자체가 실패하면 `recovery_required`로 보고하고 해당 플러그인 실행 중 추가 파일 작업을 차단합니다. **파일 변경 성공은 ‘적용 대기’이며 실제 게임 리로드 성공이 아닙니다.** 적용 대기·완료 기록은 메모리 상태이며 외부에서 수행한 파일 변경이나 리로드는 관리 이력으로 추적하지 않습니다.

작업 취소는 세션 객체 및 UUID/connectionId에 연결됩니다. 최종 메인 스레드 권한 확인 뒤, quit/revoke와 같은 메모리 잠금으로 커밋 권한을 1회 확정합니다. 취소가 먼저 확정되면 파일 변경을 하지 않습니다. 커밋 권한 확정이 먼저면 바로 이어지는 단일 원자 파일 작업은 진행 중인 작업으로 취급합니다. 이후 로그아웃으로 이미 시작된 원자 작업을 소급 취소하지는 않습니다. 이 잠금 안에서는 디스크 I/O를 수행하지 않아 서버 틱이 디스크 완료를 기다리지 않습니다. 권한 변경은 별도 이벤트/틱 순회 없이 최종 요청 검사 시점에 판단합니다.

백업 수동 복구는 서버를 정상 종료하고 해당 팩 파일명의 UTF-8 SHA-256 접두어로 `.bak`을 찾아 내용과 시각을 확인한 뒤 원래 ZIP 이름으로 복사하는 운영자 작업입니다. 웹 백업 복원 버튼은 제공하지 않습니다. 강제 전원 종료의 디스크 영속성, 관리자/다른 플러그인의 동시 파일 변경까지 트랜잭션으로 보장하지 않으므로 관리 폴더의 OS 쓰기 권한은 신뢰된 서버 계정에만 부여하고 외부 편집과 웹 작업을 겹치지 않게 운영합니다. 감사 로그에는 플레이어 UUID·작업 종류·작업 ID·결과 코드만 기록하며 비밀 값과 경로를 남기지 않습니다.

## 변경사항 적용

ZIP 파일 작업은 자동 데이터 리로드를 하지 않습니다. 여러 변경은 서버 공통 대기 목록에 모이고, **변경사항 적용 → 변경 목록 확인 → 확인 후 적용**으로 한 번에 반영합니다. 확인 이후 다른 관리자가 파일을 변경하면 revision 검증이 실패해 새 목록을 다시 확인해야 합니다. 파일 작업 중에는 적용을, 적용 중에는 파일 작업/추가 적용을 서버가 거부합니다. 적용 대기 항목이 없으면 실행할 수 없습니다.

```yaml
apply:
  cooldown-seconds: 30  # 1..3600, 기본 30초
```

쿨타임은 모든 계정/세션이 공유하며 **리로드 시도가 끝난 때부터** 계산합니다. 성공/실패 모두 적용하며 `System.nanoTime()` 기반으로 API 요청 시 판단합니다. 서버 틱 스케줄러는 추가하지 않습니다. 브라우저 카운트다운은 표시용이며 서버는 쿨타임 중 429 + Retry-After를 반환합니다. 파일 편집은 쿨타임 중에도 가능하지만 재적용은 기다려야 합니다.

상태는 적용 완료(대기 없음), 적용 대기, 적용 중, 적용 성공, 적용 실패와 쿨타임으로 구분합니다. 기존 5초 세션 확인 응답에 상태를 포함하며 별도 상시 폴링은 없습니다. 수동 조회/확인에는 `GET /api/apply`, 실행에는 `POST /api/packs/apply`를 사용합니다. POST는 Origin·세션·CSRF와 `X-Apply-Revision`이 필수이고 본문을 받지 않습니다. 리로드 전에 재확인한 접속권이 유효해야 시작합니다. 이미 시작된 리로드는 세션 종료로 무리하게 취소하지 않습니다.

리로드는 다음 메인 스레드 작업에서 공개 `Server.reloadData()`를 한 번 호출합니다. 긴 작업을 HTTP 인증 게이트의 타임아웃과 묶지 않습니다. **Paper 26.3-211에서 공식 완료 이벤트 1회와 호출 정상 반환을 모두 확인해야 성공**으로 처리합니다. 실패/완료 확인 불가 시 대기 항목을 남기고 쿨타임 후 재시도합니다. 확인 불가 시 원본 실패 이유는 공개 API가 제공하지 않으므로 서버 로그를 확인해야 합니다. 주 스레드 응답 지연 중에는 화면을 잠시 숨기고 기존 세션 확인 주기로 재검증합니다.

`setEnabled()`를 웹 스위치에서 즉시 호출하지 않습니다. 여러 활성 상태를 한 번에 적용하는 공개 API가 없으므로 웹 활성화/비활성화 예약·실행은 현재 모두 제한합니다. 새로 추가한 팩은 `reloadData()`의 기본 선택 동작에 의해 명시적 적용 시 활성화될 수 있습니다. 내장/플러그인/폴더 보호와 활성 팩 삭제 금지는 유지합니다.

완료 판정을 검증하지 않은 서버 빌드에서는 웹 적용만 비활성화합니다. 공식 성공 이벤트는 모든 함수·레시피·게임 상태의 정상 동작까지 보증하지 않습니다. 다른 플러그인/콘솔의 외부 리로드를 강제로 직렬화할 API도 없으므로 겹치지 않게 운영해야 합니다. 메모리 대기 상태가 유실되는 플러그인 핫 리로드는 지원하지 않으며 정상 서버 재시작을 사용합니다. 정상 재시작 시 서버 자체가 디스크의 데이터팩을 로드하고 이전 세션은 폐기됩니다.

## 빌드

필요 도구: JDK **25**, Node **24.22.1**, npm **11.19.1**. Gradle **9.8.2**는 체크섬이 고정된 Wrapper가 내려받습니다.

```bash
./gradlew build
```

Windows에서는 `gradlew.bat build`. Gradle은 `npm ci` → TypeScript 검사·Vite 빌드 → Java 컴파일 → JAR 패키징을 수행합니다. 실행 시에는 Node/npm/Gradle이 필요하지 않습니다.

결과: `build/libs/remote-datapack-1.0.0.jar`.

`gradle.lockfile`, `gradle/verification-metadata.xml`, `frontend/package-lock.json`으로 의존성을 고정합니다. Paper API는 `compileOnly`이며 JAR에 포함하지 않습니다. 운영 라이브러리를 런타임에 추가 다운로드하는 플러그인 설정도 없습니다. 빌드 산출물의 파일 순서와 타임스탬프를 고정합니다.

## 외부 접속과 인증 경계

웹 바인딩은 **루프백 IP만 허용**합니다. `0.0.0.0`, 사설/공인 IP, DNS 이름으로 직접 HTTP를 공개하는 설정은 거부합니다. 기본 설정은 인증을 열지 않습니다. HTTPS 공개 URL 또는 명시적 로컬 개발 설정이 필요합니다.

외부 접속 시 운영자가 같은 네트워크 네임스페이스에서 접근 가능한 HTTPS 리버스 프록시를 구성하고, `web.public-url`에 `https://packs.example.com` 같은 **HTTPS origin**을 설정해야 합니다. 프록시는 Host를 해당 호스트명 또는 `localhost`로 전달해야 합니다. 경로 접두어, userinfo, query, fragment는 허용하지 않습니다. `X-Forwarded-*`로 공개 URL이나 권한을 결정하지 않습니다. 프록시에도 요청 크기·연결 수·헤더 시간 제한을 설정합니다.

Docker에서 컨테이너의 `127.0.0.1`은 호스트나 다른 프록시 컨테이너의 루프백과 다릅니다. 포트 publish만 추가해도 이 리스너에는 연결되지 않습니다. HTTPS 프록시는 Minecraft 컨테이너의 루프백 리스너에 접근할 수 있는 네트워크 구성이 필요합니다.

운영 설정 예시:

```yaml
web:
  public-url: "https://packs.example.com"
  local-development: false
auth:
  trust-proxy-identity: false
  link-ttl-seconds: 60
  max-sessions-per-player: 1
  idle-timeout-minutes: 30
  session-ttl-minutes: 30
```

실제 `config.yml`의 다른 필드는 그대로 유지합니다. 운영 쿠키는 `__Host-remotedatapack_session; Secure; HttpOnly; SameSite=Strict; Path=/`이며 Domain은 없습니다. 세션 ID와 토큰은 SHA-256 해시를 키로 메모리에만 저장합니다. 쿠키는 브라우저 세션 쿠키지만 서버는 기본 30분 절대 만료와 30분 유휴 만료를 검사합니다. 폴링은 유휴 시간을 갱신해도 절대 만료를 연장하지 않습니다.

`online-mode=true`를 기본 신원 근거로 사용합니다. 오프라인 모드는 인증을 차단합니다. 인증된 프록시 전달 및 직접 게임 접속 차단을 운영자가 보장한 경우에만 `auth.trust-proxy-identity: true`를 명시할 수 있습니다. 이 설정은 프록시 인증을 구현하거나 검증하지 않습니다.

로컬 HTTP 개발은 `web.local-development: true`, 빈 `web.public-url`로만 활성화합니다. 이때 별도 이름 `remotedatapack_dev_session`과 `HttpOnly; SameSite=Strict; Path=/`를 사용하며 Secure만 생략합니다. 바인딩된 루프백 IP와 실제 포트로 링크를 만들고 프록시 공개 URL과 함께 설정하면 시작을 거부합니다. 이 개발 모드를 외부에 게시하지 마세요.

인증 링크는 `/#/auth/<token>` 형태입니다. fragment는 HTTP 요청·Referer에 들어가지 않으며 JS가 즉시 주소창에서 제거하고 동일 출처 JSON POST로 교환합니다. 브라우저는 동일 출처 자산만 요청하며, 스킨 이미지는 서버가 공식 텍스처 서버에서 가져와 전달합니다. `no-referrer`, CSP, `no-store`, `nosniff`, 프레임 차단을 유지합니다. 토큰·쿠키·CSRF 값과 접근 URL은 플러그인 로그에 기록하지 않습니다. 프록시에서도 요청 본문·Cookie·Set-Cookie를 수집하지 않도록 설정하세요. 링크를 탈취해 먼저 사용한 사람은 세션을 얻을 수 있으므로 공유하면 안 됩니다.

인증 교환·로그아웃·파일 변경은 정확한 Origin을 요구합니다. 로그아웃과 파일 변경에는 세션별 CSRF 헤더도 필요합니다. CORS를 허용하지 않고 `X-Forwarded-*`를 권한 근거로 삼지 않습니다. 토큰 교환은 최대 256바이트 JSON과 전역 버스트 20회/초당 5회 충전 제한을 사용합니다. 실패 응답은 400/401/403/405/411/413/415/429/503이며 비밀값을 반사하지 않습니다.

HTTP 워커는 최대 32개 대기 작업·2초 제한의 메인 스레드 통로로 인증 판정을 요청합니다. 플레이어 조회·온라인 상태·권한 검사는 Paper 메인 스레드에서만 실행하며 틱 스레드는 HTTP 완료를 기다리지 않습니다. 타임아웃된 미실행 작업은 나중에 인증 상태를 변경하지 않습니다. 이미 완료된 인증 응답이 게임 종료와 엇갈려 도착하더라도 그 쿠키는 이후 요청에서 거부됩니다.

접속 종료는 `PlayerQuitEvent`에서 해당 접속의 토큰과 세션을 즉시 회수합니다. 매 틱 반복 작업이나 전체 플레이어 권한 순회는 없습니다. 권한은 링크 발급과 해당 웹 인증 요청이 있을 때만 검사합니다. 열린 웹 화면의 기존 5초 세션 폴링도 이 요청에 포함됩니다. 요청 사이에 권한을 회수했다가 복구하면 그 중간 변화는 관측하지 않으며, 권한이 없는 상태에서 다음 요청이 오면 관련 자격 증명을 회수합니다.

별도 서버 종료 이벤트는 구독하지 않습니다. `onDisable()`은 플러그인만 비활성화되는 경우에도 웹 리스너·워커·대기 작업을 닫고 메모리 인증 정보를 정리하기 위해 유지합니다. 만료는 사용 시 검사하며 링크 발급·상태 조회 때 해당 계정의 만료된 항목을 정리합니다. 미사용 항목도 접속당 링크/세션 각 1개로 제한되고 접속 종료 때 삭제됩니다.

플러그인 업데이트는 정상 서버 종료 후 JAR를 교체하고 다시 시작합니다. 업데이트 전 월드와 플러그인 설정을 백업합니다. 재시작하면 기존 웹 세션이 종료되므로 새 `/rdpack` 링크가 필요합니다. 활성화/비활성화 일괄 변경은 현재 지원하지 않습니다.
