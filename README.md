# Remote Datapack

[![Buy Me a Coffee](https://img.shields.io/badge/Buy_Me_a_Coffee-Support_Manafield-FFDD00?style=for-the-badge&logo=buymeacoffee&logoColor=000000)](https://buymeacoffee.com/manafield)

게임에 접속한 관리자가 웹에서 데이터팩을 관리하는 Paper 플러그인입니다. **1.3.0부터 Paper 1.21.9 이상으로 지원 범위를 확대**하며, 지원 버전에서 같은 JAR를 사용합니다.

[**최신 릴리스 · 1.3.0 다운로드**](https://github.com/eventide-manafield/remote-datapack/releases/tag/1.3.0)

## 지원 버전

**`remote-datapack-1.3.0.jar` 하나를 아래 모든 지원 버전에서 사용합니다.** Java는 플러그인의 최소 요구사항뿐 아니라 실행할 Paper 서버의 요구사항도 충족해야 합니다.

| Minecraft / Paper 버전 | 필요한 Java | 데이터팩 형식 | 실제 실행·웹 적용 검증 Paper 빌드 |
|---|---|---|---|
| 1.21.9 | 21 이상 | 88.0 | 59 |
| 1.21.10 | 21 이상 | 88.0 | 130 |
| 1.21.11 | 21 이상 | 94.1 | 132 |
| 26.1.1 | 25 이상 | 101.1 | 29 |
| 26.1.2 | 25 이상 | 101.1 | 74 |
| 26.2 | 25 이상 | 107.1 | 134 |
| 26.3 | 25 이상 | 121.0 | 211, 218 |

- **Java 21 호환 JAR여도 26.1 이상 서버는 Java 25 이상이 필요합니다.** 실제 실행 검증은 1.21.x에서 Java 21, 26.x에서 Java 25로 진행했습니다. Java 요구사항은 [Paper 공식 문서](https://docs.papermc.io/paper/getting-started/#requirements)를 참고하세요.
- 표에 있는 Minecraft 버전의 다른 Paper 빌드에서는 웹 인증·파일 관리·템플릿 생성을 제공하지만, **변경사항 적용은 위 검증 빌드에서만 활성화**합니다.
- **1.21.9 이전 버전과 표에 없는 Minecraft 버전·스냅샷은 지원하지 않습니다.** 향후 버전까지 자동으로 호환된다는 의미는 아니며, 미등록 버전에서는 플러그인을 비활성화합니다.
- Paper용 플러그인으로, Spigot·Folia 및 다른 서버 구현체의 호환성은 보증하지 않습니다.

Paper 1.21.9-59와 26.1.1-29는 공식 다운로드의 ALPHA 빌드로 호환성을 확인했습니다. 공식 Paper 다운로드에 26.1 단독 버전은 없어, 26.1 계열의 실제 지원·검증 대상은 26.1.1과 26.1.2입니다.

## 현재 기능

- `/remotedatapack` 또는 `/rdpack`: 접속 중이며 `remotedatapack.manage` 권한을 가진 플레이어에게 본인용 일회용 링크 발급. 권한 기본값은 `op`입니다.
- `/rdpack status`: 본인의 링크·세션 개수와 웹 구동 상태. 콘솔에서는 구동 상태만 확인합니다.
- `/rdpack revoke`: 해당 플레이어의 모든 미사용 링크와 웹 세션 회수.

- 웹의 **새 데이터팩 만들기**: 현재 서버 버전에 맞는 템플릿 ZIP 다운로드. 네임스페이스·작성자·설명을 입력합니다.

## 빠른 설정 · 직접 HTTP

JAR를 `plugins/`에 넣고 서버를 시작한 뒤, 생성된 `plugins/RemoteDatapack/config.yml`에서 외부 주소를 입력합니다.

```yaml
web:
  mode: direct-http
  bind: 0.0.0.0
  port: 13532
  public-url: "http://mc.example.com:13532"
  local-development: false
```

`mc.example.com` 대신 서버의 공인 IP 또는 도메인을 사용하세요. 서버를 정상 재시작하고, 방화벽과 공유기에서 **TCP 13532**를 허용·포트포워딩합니다. Docker에서는 컨테이너 포트도 게시해야 합니다. 게임 접속 포트와 별개이며 UDP는 필요하지 않습니다. 외부 포트를 다르게 연결했다면 `public-url`에는 외부 포트를 입력합니다.

게임에서 `/rdpack`을 실행하면 설정한 주소의 인증 링크가 발급됩니다. 주소를 비워두면 인증이 비활성화됩니다. 이미 쓰는 포트라면 다른 번호로 변경하세요. 설정은 정상 재시작 후 반영됩니다.

**직접 HTTP는 암호화되지 않습니다.** 인증 정보와 파일 전송을 암호화하려면 아래 HTTPS 프록시 모드를 사용하세요. Cloudflare DNS를 이용할 때 직접 접속 주소는 **DNS only**로 설정합니다. HSTS가 적용된 도메인에서는 브라우저가 HTTPS로 바꿀 수 있으므로 별도 주소 또는 HTTPS 모드를 사용하세요.

1.3.0에서는 헤더 크기 제한 옵션을 실제 JDK 속성인 `sun.net.httpserver.maxReqHeaderSize`로 확인합니다. 이전 안내의 `jdk.httpserver.maxReqHeaderSize`를 사용 중이라면 시작 명령에서 아래 옵션으로 바꿔 주세요. 잘못된 옵션만 있으면 웹 리스너를 열지 않습니다.

내장 웹서버의 연결·헤더 제한을 위해 아래 JVM 옵션을 서버 시작 명령의 `-jar` 앞에 넣어야 합니다. 기존 설치에 이미 있다면 유지합니다.

```text
-Dsun.net.httpserver.maxReqTime=10 -Dsun.net.httpserver.maxRspTime=10 -Djdk.httpserver.maxConnections=64 -Dsun.net.httpserver.maxReqHeaders=64 -Dsun.net.httpserver.maxReqHeaderSize=16384
```

## 사용 예시

1. 게임에 접속한 관리자가 `/rdpack`을 입력합니다. `remotedatapack.manage` 권한이 필요하며 기본값은 OP입니다.
2. 채팅에 표시된 일회용 링크를 60초 안에 엽니다. 인증되면 계정명과 스킨 얼굴이 표시됩니다.
3. ZIP을 선택해 추가하거나 기존 ZIP을 교체합니다. 여러 파일을 변경해도 게임 데이터는 자동으로 리로드되지 않습니다.
4. **변경사항 적용**을 누르고 변경 목록을 확인한 뒤 **확인 후 적용**을 누릅니다. 적용 종료 후 기본 30초의 서버 공통 쿨타임이 시작됩니다.
5. 게임에서 로그아웃하면 웹 세션도 종료됩니다. 재접속 후에는 `/rdpack`으로 새 링크를 발급받습니다.

스킨 이미지를 불러오지 못하면 이름의 첫 글자를 표시합니다.

```yaml
ui:
  server-name: "Manafield"
  session-poll-seconds: 5
apply:
  cooldown-seconds: 30
```

서버명과 쿨타임 설정 변경은 정상 서버 재시작 후 적용됩니다.

## 서버 버전과 템플릿

지원 버전·Java 요구사항·데이터팩 형식과 웹 적용 검증 빌드는 위 **지원 버전** 표를 따릅니다. 플러그인 바이트코드는 Java 21을 대상으로 빌드합니다.

템플릿의 대상 버전은 서버에서 결정하며 클라이언트가 지정하지 않습니다. ZIP에는 `pack.mcmeta`, 작성자·버전 안내를 담은 `README.txt`, 주석만 있는 `data/<namespace>/function/main.mcfunction`을 넣습니다. `load`/`tick` 자동 실행 등록, 서버 파일 생성, 데이터 리로드는 하지 않습니다. 내용을 작성한 뒤 기존 ZIP 업로드와 변경사항 적용을 사용하세요.

작성자는 Minecraft 표준 메타데이터 필드가 아니므로 `README.txt`에 기록합니다. 네임스페이스는 영문 소문자·숫자로 시작하는 1–64자(`a-z`, `0-9`, `_`, `.`, `-`)이며 `minecraft`는 허용하지 않습니다. 작성자는 1–80자, 설명은 1–512자로 제한하며 제어 문자·줄바꿈을 거부합니다.

`GET /api/templates`는 대상 버전 정보를 반환하고 `POST /api/templates`는 `namespace`, `author`, `description` JSON을 받아 ZIP을 반환합니다. 인게임 연동 세션·권한 검사를 사용하며 POST에는 정확한 Origin과 세션 CSRF 토큰이 필요합니다. 요청은 8 KiB 이하로 제한하고 ZIP은 메모리에서만 생성합니다. 생성 후에도 세션을 다시 검증합니다.

버전 정보는 공식 Paper 배포 JAR에 포함된 Mojang `version.json`의 `pack_version`을 확인해 고정했습니다. 형식 변경 근거는 [Minecraft 1.21.9 변경 내역](https://www.minecraft.net/en-us/article/minecraft-java-edition-1-21-9), Java 요구사항은 [Paper 공식 문서](https://docs.papermc.io/paper/getting-started/#requirements)를 참고하세요. 빌드는 공식 저장소의 `paper-api:1.21.9-R0.1-SNAPSHOT`(확인한 아티팩트: `20251007.115206-20`)을 사용합니다. 과거 POM의 Adventure SNAPSHOT 의존성 대신 API JAR와 필요한 컴파일 전용 타입의 버전을 명시하고, 의존성 잠금 및 SHA-256 검증을 유지합니다. API 아티팩트가 바뀌면 체크섬 검증에 실패하므로 검토 없이 새 내용을 받아들이지 않습니다. Paper API와 컴파일 전용 의존성은 배포 JAR에 넣지 않으며 서버에 따로 설치할 필요도 없습니다.

## 데이터팩 목록과 보호 정책

`packs.directory: auto`는 실제 메인 월드의 `datapacks/`를 사용합니다. 1.21.x에서는 공개 `Server.getWorld(minecraft:overworld)`와 `World.getWorldPath()`로 정식 오버월드를 찾고, 26.1 이상에서는 공개 `Server.getLevelDirectory()`를 사용합니다. 최신 메서드의 연결은 공개 Server 인터페이스에 한정한 리플렉션으로 분리하여 구버전에서 클래스 로딩이 실패하지 않게 합니다. 내부 서버 클래스나 `UnsafeValues`를 사용하지 않습니다. 경로를 확인할 수 없으면 파일 관리는 읽기 전용으로 남깁니다. 첫 번째 로드된 월드를 추측하거나 사용자 요청의 경로를 받지 않습니다. 명시 경로를 설정하려면 이 동일한 디렉터리의 정규화된 절대 경로여야 합니다. 다른 월드·경로, 안전하지 않은 경로 또는 지원하지 않는 파일시스템이면 로컬 연결을 포기하고 Paper 정보만 보호 상태로 표시합니다.

- **ZIP/폴더**: Paper 출처가 WORLD이고 `file/<단일 파일명>`과 실제 로컬 항목이 일치할 때만 연결합니다. 폴더는 루트 `pack.mcmeta` 존재 여부만 확인하며 내용을 파싱하거나 하위를 재귀 탐색하지 않습니다.
- **내장·플러그인 팩**: Paper의 출처 값으로 구분하고 보호합니다. 같은 파일명이 있어도 파일 조작 대상으로 취급하지 않습니다.
- **새 로컬 후보**: Paper 목록에 아직 없는 `.zip` 또는 메타데이터가 있는 폴더는 `서버 미인식`, 활성 상태 `확인 불가`로 표시합니다. ZIP이나 JSON의 유효성을 검사했다는 뜻이 아닙니다.
- **경로 보호**: 디렉터리 핸들을 이용한 `SecureDirectoryStream`과 NOFOLLOW_LINKS로 루트의 모든 경로 구성요소를 엽니다. 심볼릭 링크는 따라가지 않으며 ZIP 하드링크 또는 링크 수를 확인할 수 없는 파일은 보호합니다. Unix 링크 수를 읽을 때 디렉터리 핸들의 파일 식별자와도 비교합니다.
- **응답 정보**: 서버 경로·원본 API 경로 ID는 노출하지 않습니다. 항목 ID는 프로세스별 난수로 구분한 불투명 값입니다. 일치한 비필수 WORLD ZIP만 `modifiable`/`downloadable`을 제공하며 `deletable`은 비활성 ZIP에서만 true입니다. 실제 작업 시 ZIP 내용과 현재 권한을 다시 검증합니다. `protected`는 내장·폴더·필수 팩·미확인 위치 등의 추가 보호 사유를 구분합니다.

목록은 로그인 직후와 `목록 다시 조회` 버튼을 누를 때만 읽습니다. 매 틱 검사나 목록 백그라운드 폴링은 없습니다. 기존 세션 확인은 5초 간격으로 유지합니다. 동시에 1개 조회, 디렉터리 항목 최대 1,024개 검사, 응답 최대 512개로 제한하고 초과 시 목록이 일부임을 표시합니다.

Paper 메타데이터는 메인 스레드에서 불변 값으로 복사하고 파일 메타데이터 조회·JSON 생성은 HTTP 워커에서 수행합니다. 파일 조회 전후 세션·권한을 확인해 조회 도중 로그아웃해도 목록을 반환하지 않습니다. 오류 응답에 예외 메시지나 경로를 포함하지 않습니다.

`목록 다시 조회`는 현재 Paper 스냅샷과 로컬 후보를 다시 읽을 뿐 `refreshPacks()`, `setEnabled()`, `reloadData()`를 호출하지 않습니다. 파일을 외부에서 추가해도 서버가 인식한 활성 상태는 자동으로 바뀌지 않습니다.

## ZIP 파일 작업

- **추가**: `POST /api/packs/upload`, `Content-Type: application/zip`, 정확한 Content-Length, 원본 ZIP 본문. multipart/전송 압축/chunked는 지원하지 않습니다. 브라우저가 File 객체로 요청하며 서버는 `rd-<UUID>.zip` 새 이름을 붙입니다. 클라이언트 파일명이나 경로로 덮어쓰지 않습니다.
- **교체**: `POST /api/packs/{id}/replace`, ZIP 본문과 `X-Pack-Confirm`에 URL 인코딩한 정확한 기존 파일명. UI에서 파일명 재입력 후 확인합니다. 활성 ZIP도 교체할 수 있지만 실행 중인 게임 데이터는 바뀌지 않습니다.
- **삭제**: `DELETE /api/packs/{id}`, 같은 파일명 확인 헤더, 본문 없음. 활성·필수·내장·플러그인·폴더·미인식 팩은 거부합니다. 활성 팩 비활성화는 공식 일괄 API 제약으로 제한합니다.
- **다운로드**: `GET /api/packs/{id}/download`. 안전한 ZIP 전체를 먼저 검증하고 attachment로 스트리밍합니다. 세션이 취소되면 이후 청크 전송을 중단하지만 이미 받은 바이트는 회수할 수 없습니다.
- **작업**: 변경 요청은 수신이 끝나면 202와 작업 ID를 반환합니다. `GET /api/jobs/{id}`는 작업을 시작한 동일 웹 세션만 조회합니다. 최근 128개를 메모리에 보관하며 재시작 시 사라집니다. 수신·검증·백업·커밋·발견 갱신·적용 대기/실패 상태를 제공합니다. 변경 중 전체 파일 작업은 1개로 제한하고 다른 요청은 409로 거부합니다.

파일 수신·검증·백업·rename·삭제·다운로드는 전용 I/O 스레드 1개에서 수행합니다. HTTP 스레드는 업로드 수신/다운로드를 최대 8초 기다리며 파일 작업 자체 기한은 30초입니다. 느린 업로드는 실패할 수 있습니다. HTTP 성공 응답을 잃으면 작업 결과도 불명확할 수 있으므로 자동 재시도하지 말고 목록과 감사 로그를 확인하세요.

ZIP 제한은 최대 20 MiB(설정 1–20), 항목 10,000개, 중앙 디렉터리 4 MiB, 선언/실제 비압축 총량 128 MiB, 항목 압축 비율 100:1, `pack.mcmeta` 64 KiB, JSON 깊이 32입니다. 경로 조작·중복 항목·심볼릭 링크/특수 파일·Unix 링크 확장·암호화·CRC/크기 불일치를 거부합니다. ZIP64·다중 볼륨·아카이브 주석·알 수 없는 확장 필드도 보수적으로 거부합니다. 압축 내용은 버퍼로 검사할 뿐 파일로 추출하지 않습니다. 현대 `min_format`/`max_format` 숫자 또는 `[major, minor]` 형식으로 현재 서버의 데이터팩 형식 지원을 명시해야 하며 레거시 메타데이터 자동 변환은 하지 않습니다. 정수 `min_format`은 해당 major의 minor 0부터, 정수 `max_format`은 해당 major의 모든 minor까지 포함하며 `[major, minor]`는 정확한 경계를 지정합니다. 게임 함수의 의미나 안전성까지 검증하는 기능은 아닙니다.

교체/삭제 전 현재 ZIP을 검증하고 같은 디렉터리의 `.rd-backup-<파일명 SHA256>-<UUID>.bak`에 별도 복사합니다. 기본 팩당 3개(1–10), 전체 200 MiB(업로드 한도–1024 MiB)입니다. 총량은 새 백업까지 포함해 미리 확인하며 부족하면 원본을 바꾸지 않습니다. 다른 팩 백업을 자동 삭제하지 않습니다. 새 백업 검증 후 같은 팩의 오래된 백업을 정리합니다. 삭제 후에도 백업은 보관합니다. `.bak`와 `.rd-tmp-<UUID>.tmp`는 팩 ZIP으로 발견되지 않습니다. 중단된 임시 파일은 정상 실패/종료 때 정리하며, 강제 종료 잔여물은 다음 변경 작업 시작 시 제한된 이름만 정리합니다.

교체는 `SecureDirectoryStream.move()`의 원자적 rename만 사용합니다. 지원하지 않으면 부분 덮어쓰기로 대체하지 않습니다. 기존 원본 해시와 백업을 확인하고 변경 후 Paper `refreshPacks()`와 `getPack()`으로 발견 상태를 확인합니다. 갱신 실패 시 백업으로 복원하거나 새 ZIP을 제거합니다. 복원 자체가 실패하면 `recovery_required`로 보고하고 해당 플러그인 실행 중 추가 파일 작업을 차단합니다. **파일 변경 성공은 ‘적용 대기’이며 실제 게임 리로드 성공이 아닙니다.** 적용 대기·완료 기록은 메모리 상태이며 외부에서 수행한 파일 변경이나 리로드는 관리 이력으로 추적하지 않습니다.

작업 취소는 세션 객체 및 UUID/connectionId에 연결됩니다. 최종 메인 스레드 권한 확인 뒤, quit/revoke와 같은 메모리 잠금으로 커밋 권한을 1회 확정합니다. 취소가 먼저 확정되면 파일 변경을 하지 않습니다. 커밋 권한 확정이 먼저면 바로 이어지는 단일 원자 파일 작업은 진행 중인 작업으로 취급합니다. 이후 로그아웃으로 이미 시작된 원자 작업을 소급 취소하지는 않습니다. 이 잠금 안에서는 디스크 I/O를 수행하지 않아 서버 틱이 디스크 완료를 기다리지 않습니다. 권한 변경은 별도 이벤트/틱 순회 없이 최종 요청 검사 시점에 판단합니다.

백업 수동 복구는 서버를 정상 종료하고 해당 팩 파일명의 UTF-8 SHA-256 접두어로 `.bak`을 찾아 내용과 시각을 확인한 뒤 원래 ZIP 이름으로 복사하는 운영자 작업입니다. 웹 백업 복원 버튼은 제공하지 않습니다. 강제 전원 종료의 디스크 영속성, 관리자/다른 플러그인의 동시 파일 변경까지 트랜잭션으로 보장하지 않으므로 관리 폴더의 OS 쓰기 권한은 신뢰된 서버 계정에만 부여하고 외부 편집과 웹 작업을 겹치지 않게 운영합니다. 감사 로그에는 플레이어 UUID·작업 종류·작업 ID·결과 코드만 기록하며 비밀 값과 경로를 남기지 않습니다.

## 변경사항 적용

ZIP 파일 작업은 자동 데이터 리로드를 하지 않습니다. 여러 변경은 서버 공통 대기 목록에 모이고, **변경사항 적용 → 변경 목록 확인 → 확인 후 적용**으로 한 번에 반영합니다. 확인 이후 다른 관리자가 파일을 변경하면 revision 검증이 실패해 새 목록을 다시 확인해야 합니다. 파일 작업 중에는 적용을, 적용 중에는 파일 작업/추가 적용을 서버가 거부합니다. 적용 대기 항목이 없으면 실행할 수 없습니다.

```yaml
apply:
  cooldown-seconds: 30  # 1..3600, 기본 30초
```

쿨타임은 모든 계정/세션이 공유하며 **리로드 시도가 끝난 때부터** 계산합니다. 성공/실패 모두 적용하며 `System.nanoTime()` 기반으로 API 요청 시 판단합니다. 서버 틱 스케줄러는 추가하지 않습니다. 브라우저 카운트다운은 표시용이며 서버는 쿨타임 중 429 + Retry-After를 반환합니다. 파일 편집은 쿨타임 중에도 가능하지만 재적용은 기다려야 합니다.

상태는 적용 완료(대기 없음), 적용 대기, 적용 중, 적용 성공, 적용 실패와 쿨타임으로 구분합니다. 기존 5초 세션 확인 응답에 상태를 포함하며 별도 상시 폴링은 없습니다. 수동 조회/확인에는 `GET /api/apply`, 실행에는 `POST /api/packs/apply`를 사용합니다. POST는 Origin·세션·CSRF와 `X-Apply-Revision`이 필수이고 본문을 받지 않습니다. 리로드 전에 재확인한 접속권이 유효해야 시작합니다. 이미 시작된 리로드는 세션 종료로 무리하게 취소하지 않습니다.

리로드는 다음 메인 스레드 작업에서 공개 `Server.reloadData()`를 한 번 호출합니다. 긴 작업을 HTTP 인증 게이트의 타임아웃과 묶지 않습니다. **위 표의 검증 빌드에서 공식 완료 이벤트 1회와 호출 정상 반환을 모두 확인해야 성공**으로 처리합니다. 실패/완료 확인 불가 시 대기 항목을 남기고 쿨타임 후 재시도합니다. 확인 불가 시 원본 실패 이유는 공개 API가 제공하지 않으므로 서버 로그를 확인해야 합니다. 주 스레드 응답 지연 중에는 화면을 잠시 숨기고 기존 세션 확인 주기로 재검증합니다.

`setEnabled()`를 웹 스위치에서 즉시 호출하지 않습니다. 여러 활성 상태를 한 번에 적용하는 공개 API가 없으므로 웹 활성화/비활성화 예약·실행은 현재 모두 제한합니다. 새로 추가한 팩은 `reloadData()`의 기본 선택 동작에 의해 명시적 적용 시 활성화될 수 있습니다. 내장/플러그인/폴더 보호와 활성 팩 삭제 금지는 유지합니다.

완료 판정을 검증하지 않은 서버 빌드에서는 웹 적용만 비활성화합니다. 공식 성공 이벤트는 모든 함수·레시피·게임 상태의 정상 동작까지 보증하지 않습니다. 다른 플러그인/콘솔의 외부 리로드를 강제로 직렬화할 API도 없으므로 겹치지 않게 운영해야 합니다. 메모리 대기 상태가 유실되는 플러그인 핫 리로드는 지원하지 않으며 정상 서버 재시작을 사용합니다. 정상 재시작 시 서버 자체가 디스크의 데이터팩을 로드하고 이전 세션은 폐기됩니다.

## 외부 접속과 인증 경계

`web.mode: direct-http`는 외부 IP 바인딩과 HTTP 공개 주소를 허용합니다. `web.mode: https-proxy`는 루프백 바인딩과 HTTPS 공개 주소만 허용합니다. 기존 설정에 `web.mode`가 없으면 HTTPS 프록시 모드로 해석하므로 업데이트만으로 외부 HTTP 접속이 열리지 않습니다. 기존에 명시한 포트도 유지됩니다.

HTTPS 프록시 모드에서는 운영자가 루프백 리스너에 접근 가능한 리버스 프록시를 구성합니다. Docker의 컨테이너 루프백은 호스트 루프백과 다르므로 같은 네트워크 네임스페이스 등 적절한 연결이 필요합니다. 프록시는 Host를 공개 주소 또는 `localhost`로 전달하고 요청 크기·연결 수·헤더 시간 제한을 설정합니다.

모든 모드에서 경로 접두어, userinfo, query, fragment가 붙은 공개 주소는 거부합니다. `X-Forwarded-*`로 공개 URL이나 권한을 결정하지 않습니다. 직접 HTTP에서는 설정된 공개 Host와 포트만 받으며, 루프백 health 점검도 허용합니다.

### HTTPS로 접속하기

HTTPS는 **리버스 프록시에서 인증서를 설정**해 사용합니다. 프록시가 HTTPS 접속을 받아 플러그인의 내부 HTTP 웹서버로 전달합니다. 플러그인 자체가 인증서를 발급하거나 HTTPS 연결을 직접 받지는 않습니다.

```text
브라우저 → HTTPS :13532 [프록시] → HTTP :8765 [플러그인]
```

플러그인 설정 예시:

```yaml
web:
  mode: https-proxy
  bind: 127.0.0.1
  port: 8765
  public-url: "https://packs.example.com:13532"
  local-development: false
auth:
  trust-proxy-identity: false
  link-ttl-seconds: 60
  max-sessions-per-player: 1
  idle-timeout-minutes: 30
  session-ttl-minutes: 30
```

- `port`: 프록시가 연결할 **내부 포트**입니다. `8765`는 예시이며, 사용하지 않는 포트로 지정합니다. 기본 포트 `13532`가 자동으로 바뀌는 것은 아닙니다.
- `public-url`: 사용자가 접속할 **외부 HTTPS 주소**입니다. `/rdpack`도 이 주소로 링크를 발급합니다.
- 프록시는 외부 `13532` 포트에서 HTTPS를 받고 내부 `http://127.0.0.1:8765`로 전달하도록 설정합니다.
- 인증서는 접속 도메인에 유효해야 합니다. 기존 인증서가 해당 도메인을 포함한다면 재사용할 수 있으며, 포트 번호는 인증서에 영향을 주지 않습니다.
- HTTP 접속을 HTTPS로 전환하려면 프록시에 리다이렉트도 설정합니다. 같은 포트에서 HTTP와 HTTPS를 함께 받을 수 있는지는 사용하는 프록시의 지원 여부를 확인하세요.

**내부 포트와 외부 포트는 같을 필요가 없습니다.** 같은 네트워크 네임스페이스에서 프록시가 `0.0.0.0:13532`를 사용하면 플러그인이 `127.0.0.1:13532`를 동시에 사용할 수 없으므로 위 예시처럼 나눕니다. 별도 네트워크 네임스페이스라면 양쪽에서 같은 번호를 사용할 수 있지만, 프록시가 플러그인에 접근할 경로도 구성해야 합니다. 포트를 나누는 것은 충돌 방지를 위한 것으로 성능 차이는 없습니다.

외부에는 프록시 포트만 개방하고 플러그인의 내부 포트는 공개하지 않습니다. 실제 `config.yml`의 다른 필드는 유지하고, 변경 후에는 Minecraft 서버를 정상 재시작하세요.

> Docker에서 프록시의 `127.0.0.1`은 별도 Minecraft 컨테이너를 가리키지 않습니다. 위 예시는 프록시와 Minecraft가 같은 네트워크 네임스페이스를 사용하는 등, 프록시가 플러그인의 루프백 리스너에 접근할 수 있는 구성을 전제로 합니다.

### 세션과 인증

HTTPS 프록시 쿠키는 `__Host-remotedatapack_session; Secure; HttpOnly; SameSite=Strict; Path=/`이며 Domain은 없습니다. 세션 ID와 토큰은 SHA-256 해시를 키로 메모리에만 저장합니다. 쿠키는 브라우저 세션 쿠키지만 서버는 기본 30분 절대 만료와 30분 유휴 만료를 검사합니다. 폴링은 유휴 시간을 갱신해도 절대 만료를 연장하지 않습니다.

`online-mode=true`를 기본 신원 근거로 사용합니다. 오프라인 모드는 인증을 차단합니다. 인증된 프록시 전달 및 직접 게임 접속 차단을 운영자가 보장한 경우에만 `auth.trust-proxy-identity: true`를 명시할 수 있습니다. 이 설정은 프록시 인증을 구현하거나 검증하지 않습니다.

직접 HTTP 쿠키는 공개 주소별 이름 `remotedatapack_http_<주소 해시>`와 `HttpOnly; SameSite=Strict; Path=/`를 사용하고 Secure와 Domain은 붙이지 않습니다. HTTPS·개발 쿠키와 구분하며 포트가 다른 인스턴스 간 이름 충돌을 줄입니다. 쿠키 자체는 포트별로 격리되지 않으므로 같은 호스트의 다른 서비스도 신뢰할 수 있어야 합니다. 모드·주소 변경이나 서버 재시작 후에는 새 링크로 인증해야 합니다.

로컬 HTTP 개발은 `web.mode: https-proxy`, 루프백 바인딩, `web.local-development: true`, 빈 `web.public-url`로만 활성화합니다. 이때 별도 이름 `remotedatapack_dev_session`과 `HttpOnly; SameSite=Strict; Path=/`를 사용하며 Secure만 생략합니다. 바인딩된 루프백 IP와 실제 포트로 링크를 만들고 프록시 공개 URL과 함께 설정하면 시작을 거부합니다. 이 개발 모드를 외부에 게시하지 마세요.

인증 링크는 `/#/auth/<token>` 형태입니다. fragment는 HTTP 요청·Referer에 들어가지 않으며 JS가 즉시 주소창에서 제거하고 동일 출처 JSON POST로 교환합니다. 브라우저는 동일 출처 자산만 요청하며, 스킨 이미지는 서버가 공식 텍스처 서버에서 가져와 전달합니다. `no-referrer`, CSP, `no-store`, `nosniff`, 프레임 차단을 유지합니다. 토큰·쿠키·CSRF 값과 접근 URL은 플러그인 로그에 기록하지 않습니다. 프록시에서도 요청 본문·Cookie·Set-Cookie를 수집하지 않도록 설정하세요. 링크를 탈취해 먼저 사용한 사람은 세션을 얻을 수 있으므로 공유하면 안 됩니다.

인증 교환·로그아웃·파일 변경은 정확한 Origin을 요구합니다. 로그아웃과 파일 변경에는 세션별 CSRF 헤더도 필요합니다. CORS를 허용하지 않고 `X-Forwarded-*`를 권한 근거로 삼지 않습니다. 토큰 교환은 최대 256바이트 JSON과 전역 버스트 20회/초당 5회 충전 제한을 사용합니다. 실패 응답은 400/401/403/405/411/413/415/429/503이며 비밀값을 반사하지 않습니다.

HTTP 워커는 최대 32개 대기 작업·2초 제한의 메인 스레드 통로로 인증 판정을 요청합니다. 플레이어 조회·온라인 상태·권한 검사는 Paper 메인 스레드에서만 실행하며 틱 스레드는 HTTP 완료를 기다리지 않습니다. 타임아웃된 미실행 작업은 나중에 인증 상태를 변경하지 않습니다. 이미 완료된 인증 응답이 게임 종료와 엇갈려 도착하더라도 그 쿠키는 이후 요청에서 거부됩니다.

접속 종료는 `PlayerQuitEvent`에서 해당 접속의 토큰과 세션을 즉시 회수합니다. 매 틱 반복 작업이나 전체 플레이어 권한 순회는 없습니다. 권한은 링크 발급과 해당 웹 인증 요청이 있을 때만 검사합니다. 열린 웹 화면의 기존 5초 세션 폴링도 이 요청에 포함됩니다. 요청 사이에 권한을 회수했다가 복구하면 그 중간 변화는 관측하지 않으며, 권한이 없는 상태에서 다음 요청이 오면 관련 자격 증명을 회수합니다.

별도 서버 종료 이벤트는 구독하지 않습니다. `onDisable()`은 플러그인만 비활성화되는 경우에도 웹 리스너·워커·대기 작업을 닫고 메모리 인증 정보를 정리하기 위해 유지합니다. 만료는 사용 시 검사하며 링크 발급·상태 조회 때 해당 계정의 만료된 항목을 정리합니다. 미사용 항목도 접속당 링크/세션 각 1개로 제한되고 접속 종료 때 삭제됩니다.

플러그인 업데이트는 정상 서버 종료 후 JAR를 교체하고 다시 시작합니다. 업데이트 전 월드와 플러그인 설정을 백업합니다. 재시작하면 기존 웹 세션이 종료되므로 새 `/rdpack` 링크가 필요합니다. 활성화/비활성화 일괄 변경은 현재 지원하지 않습니다.
