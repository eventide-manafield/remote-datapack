# 아키텍처

## 구성과 실행 경계

| 구성 | 책임 |
|---|---|
| `RemoteDatapackPlugin` | 설정·지원 버전 확인, 명령어·접속 이벤트, 시작·종료 |
| `EmbeddedHttpServer` / `JettyExchange` | 독립된 HTTP/1.1 리스너와 `HttpExchange` 핸들러 연결 |
| `AccessManager` / `MainThreadGate` | 접속별 자격 증명·취소 상태와 Paper 메인 스레드 권한 검사 |
| `DatapackService` / `PaperPacks` / `LocalPackScanner` | Paper 상태와 로컬 파일을 합친 보호 목록 |
| `FileService` / `PackDirectory` / `ZipValidator` | 직렬 파일 작업, 검증·백업·원자적 변경 |
| `ApplyCoordinator` / `PaperReload` | 서버 공통 변경 목록·상호 배제·쿨타임과 리로드 완료 판정 |

Jetty와 전용 SLF4J NOP 로거는 JAR 내부의 `studio.manafield.remotedatapack.internal` 패키지로 분리됩니다. HTTP 제한은 리스너별로 적용하며 JDK HTTP 서버의 전역 속성에 의존하지 않습니다. React 정적 자산도 같은 JAR에서 제공합니다.

Paper 플레이어 조회·온라인 상태·권한·데이터팩 API는 메인 스레드에서 실행합니다. HTTP 워커는 `MainThreadGate`를 통해 최대 32개의 미완료 호출을 수용하고 2초까지 기다립니다. 만료되거나 취소된 미실행 호출은 나중에 인증 상태를 변경하지 않습니다. 메인 스레드는 HTTP 응답이나 파일 I/O 완료를 기다리지 않습니다.

파일 메타데이터·JSON 생성은 HTTP 워커, ZIP 수신·검증·백업·변경·다운로드는 전용 I/O 워커 1개가 담당합니다. 파일 작업은 다운로드까지 포함해 동시에 하나만 허용합니다. 권한 검사와 접속 종료 사이의 취소 계약은 [보안 문서](SECURITY.md#접속-수명과-작업-취소)를 따릅니다.

## 목록과 대상 경로

`packs.directory: auto`는 메인 월드의 `datapacks/`에 연결합니다. 1.21.x에서는 공개 `Server.getWorld(minecraft:overworld)`와 `World.getWorldPath()`, 26.x에서는 공개 `Server.getLevelDirectory()`를 사용합니다. 후자는 공개 인터페이스 리플렉션으로 연결해 구버전 클래스 로딩과 분리합니다. 명시 경로도 동일한 메인 월드 디렉터리로 정규화되는 값만 허용합니다. 경로를 확인할 수 없으면 로컬 파일 작업을 사용할 수 없습니다.

메인 스레드의 불변 Paper 스냅샷과 제한된 로컬 스캔을 합칩니다. WORLD 출처의 `file/<파일명>`과 안전한 로컬 파일이 일치해야 조작 대상이 됩니다. 목록의 폴더 판정은 루트 `pack.mcmeta` 존재 여부만 확인하므로 ZIP 유효성 검사와 구분됩니다. 자세한 보호 조건은 [경로와 대상 보호](SECURITY.md#경로와-대상-보호)에 있습니다.

조회는 동시에 하나, 디렉터리 검사 최대 1,024항목, 응답 최대 512팩으로 제한합니다. 조회 전후 세션·권한을 재검증합니다. UI는 최초 표시·수동 조회·파일 변경 시도 후 목록을 읽습니다. 세션은 5초 간격, 진행 중 파일 작업은 750ms 간격으로 확인합니다. 단순 목록 조회는 발견 상태 갱신이나 리로드가 아니므로 외부에서 추가한 파일의 활성 상태를 바꾸지 않습니다.

## 파일 변경 흐름

1. 세션·CSRF와 파일 작업 슬롯을 확보하고, 대상 ID를 최신 Paper 스냅샷과 로컬 스캔으로 다시 확인합니다.
2. 업로드를 임시 파일로 수신해 ZIP을 검증합니다. 교체·삭제는 기존 ZIP 검증과 별도 백업을 거칩니다.
3. 루트·원본 해시·대상·권한을 재확인하고 커밋 권한을 한 번 예약합니다. 이어서 원자적 이동 또는 파일 삭제를 수행합니다.
4. 메인 스레드에서 `refreshPacks()`와 `getPack()`으로 발견 상태를 확인합니다. 성공하면 서버 공통 변경 목록에 기록하고 작업을 `pending_apply`로 마칩니다.
5. 발견 갱신이 실패하면 새 파일을 제거하거나 백업으로 복원합니다. 복원이 실패하면 `recovery_required`를 설정해 추가 파일 작업과 적용을 차단합니다.

HTTP 측 수신·다운로드 대기는 최대 8초, 파일 작업의 협력적 기한은 30초입니다. 차단된 네트워크 읽기·쓰기는 HTTP 연결 기한으로도 제한합니다. 응답 유실이 파일 미변경을 뜻하지는 않습니다. 작업 상태와 보존 범위는 [파일 API](API.md#파일-작업)를 참조하세요.

템플릿은 서버의 `PackFormat`으로 메모리에서 생성하는 다운로드입니다. `pack.mcmeta`, 작성자 안내 `README.txt`, 주석만 있는 `data/<namespace>/function/main.mcfunction`을 포함하며 서버 파일 작업·적용 대기 목록과 분리됩니다.

## 변경사항 적용

파일 변경과 게임 데이터 리로드는 분리됩니다. `ApplyCoordinator`는 파일명별 마지막 작업을 모으고 변경마다 `revision`을 증가시킵니다. 항목이 많으면 오래된 상세 항목을 집계 표시로 대체합니다. 웹 확인 시점의 revision이 달라지면 적용을 거부해 새 목록 확인을 요구합니다.

적용과 파일 작업은 서로 배타적이며 대기 변경이 있어야 적용할 수 있습니다. 다음 메인 스레드 작업에서 접속권을 다시 확인한 뒤 `Server.reloadData()`를 한 번 호출합니다. 리로드는 2초 인증 게이트 밖에서 실행됩니다. 호출이 시작된 이후에는 로그아웃으로 취소하지 않습니다.

지원 범위는 [README 표](../README.md#지원-버전)와 `PackFormat.reloadBuilds`에 한정됩니다. Paper 브랜드·버전을 확인하고, `reloadData()` 호출 중 메인 스레드의 `ServerResourcesReloadedEvent`가 PLUGIN 원인으로 정확히 한 번 발생한 뒤 호출이 정상 반환해야 성공입니다. 완료를 확인하지 못하면 대기 변경을 남깁니다. 공개 API가 제공하지 않는 원본 실패 원인은 서버 로그에서 확인해야 합니다. 이벤트는 개별 함수·레시피가 의도대로 동작함을 보증하지 않습니다.

쿨타임은 실제 리로드 시도가 끝난 시점부터 성공·실패 모두 적용합니다. 시작 전 권한 취소나 스케줄 등록 실패는 리로드 시도로 세지 않습니다. `System.nanoTime()`으로 요청 시 남은 시간을 계산하며 브라우저 카운트다운은 표시용입니다. 적용 상태는 세션 응답에도 포함됩니다. 외부 콘솔·플러그인의 리로드는 이 상호 배제 범위 밖입니다.

웹 활성화·비활성화는 `activationSupported: false`입니다. `setEnabled()`는 리로드를 동반할 수 있고 여러 변경의 단일 리로드를 보장하는 공개 API 계약이 없어, 명시적 적용 흐름에 포함하지 않습니다.

## 종료와 재시작

`onDisable()`은 자격 증명, 메인 스레드 통로, 웹 연결과 워커를 닫고 진행 중 파일 작업에 취소를 알립니다. 세션·작업 이력·적용 대기·쿨타임은 메모리 상태입니다. 정상 재시작 시 Minecraft가 디스크의 팩을 로드하고 새 인증 링크가 필요합니다. 플러그인 핫 리로드 대신 정상 서버 종료·시작을 사용합니다.
